# Captured engineering build

For the bounded acquisition control/150 pF source recipe, start with the
[acquisition brief preparer](acquisition-prepare.md). It generates the typed
inputs consumed here; preparation does not supply native or engineering evidence.

`agent-ee build run` composes the existing requirements, parts, native scaffold,
schematic, placement/routing, artwork and final package producers. The public path is
being qualified. Fresh execution establishes the captured requirements, parts,
native schematic, placement, routing and artwork on a sourced 17-part multiblock
design. Native checks, cancellation/resumption and honest rejection also run. A complete
manufacturing run through this command remains an open requirement in the
[system acceptance map](system-acceptance.md).

```sh
agent-ee build run build.json --out NEW_RUN
agent-ee build run build.json --out EXISTING_RUN --resume
agent-ee build review EXISTING_RUN --out NEW_DIAGNOSTIC --max-seconds 900
agent-ee verify NEW_DIAGNOSTIC/review
```

Engineering choices are captured inputs: requirements and their check mappings,
circuit topology, selected parts with sourcing/CAD evidence, schematic layout,
board envelope, project rules, placement intent and functional groups. This
command does not synthesize a circuit from prose or authorize purchases or
fabrication orders.

The plan uses existing record formats:

```json
{
  "schema": "agent-ee.build-plan/1",
  "source": "captured-inputs",
  "requirements": {
    "map": "requirement-map.json",
    "record": "spec-record.json",
    "spec": "spec.md"
  },
  "parts": {
    "manifest": "parts.json",
    "circuit": "circuit.json",
    "layout": "layout.json"
  },
  "envelope": "envelope.json",
  "placement": {
    "intent": "placement.json",
    "groups": "groups.json",
    "budget_s": 1200,
    "search": {
      "seeds": [{"seed": 0, "start": "clustered"}],
      "steps_per_seed": 100000,
      "shortlist": 1
    },
    "router": {"checkout": "/opt/kicad-route"}
  },
  "verification_timeout_s": 3600
}
```

`source` is relative to the plan, or absolute. Other engineering input paths
are relative to that bundle. Router checkout semantics are those of the
[placement job](placement-job.md). The bundle includes every dependency named
by its records and the project template at the requirement map's project path.
Native schematic and PCB files are generated by the scaffold; no placeholder
native files are required. Parts may also name the existing `deviations` and
`ratings` records described in [parts production](parts-stage.md).

For declared power or ground planes, add `placement.planes: "planes.json"`.
The file uses the existing [plane-plan format](add-planes.md). The placement job
creates those zones on each selected placement before routing, then refills,
saves and independently verifies them after routing. Its shared time budget and
cancellation control cover these native processes. The original placement
candidate and engineering source files remain unchanged. A failed plane attempt
cannot become an eligible routed result.

The final DRC check must bind the same captured plan:

```json
{"id": "drc", "kind": "drc", "params": {
  "plane_plans": [{"path": "planes.json", "sha256": "<SHA-256 of the plan bytes>"}]
}}
```

This direct binding checks the final native zones against the authored plan.
Existing campaign `plane_obligations` continue to require their separate
producer/composition custody. Captured legacy reports cannot be hidden by a
direct binding. The normal placement path currently requires
`island_removal: "always"`; it rejects `never` explicitly. Existing native zones
and rule areas on the placement input still require further placement-model
support; this path creates declared zones after component placement.

Legacy plans use `agent-ee.requirement-map/1`, including its
ordinary scope/3 template and per-requirement check declarations. Its input
locations are rebound to each retained candidate without changing the mapped
requirements. When `parts.ratings` is supplied, the build captures its adopted
`compile-parts` receipt and exact report under `build-generated/parts-ratings/`
and derives `rating_provenance` on every assembly check. An authored declaration
of that parameter is refused; it must identify this build's actual producer.
The build captures compiler provenance under `requirements-map/` and accounts
for every source requirement and paragraph. A declared scope envelope also
derives its exact field requirements from the captured envelope and profile;
the same requirement map binds their IDs to checks. Once the scaffold exists,
the ordinary coverage compiler
and scaffold must reproduce the same authored acceptance baseline. For a rated
build, that comparison removes only the derived rating parameter. The final
baseline retains the parameter and immutable receipt/report hashes;
`rating-binding.json` records both baseline identities. Parts declarations
used by `parts_subset` must cite the matching requirement's exact source and
locator, including the generated `requirements-map/spec.md` source where that
requirement is declared. The existing checker enforces this identity.

The directories `requirements-map/` and `build-generated/` are reserved for
build outputs. The source bundle cannot supply either. Links and special files
in engineering inputs are refused.

Each completed stage retains a separate candidate and hash-bound directory.
Steps use ordinary `run_step` receipts and adopt only completed output. Failed
attempts remain beside subsequent attempts. The report records source hashes,
implementation and native runtime identities, completed stages, attempts and
the current candidate. Resumption checks those identities and all completed
stage files before doing more work. Changed source or saved native files require
a new build; they cannot silently become the old run's accepted output.

For diagnostics, `--through requirements`, `parts`, `scaffold`, `schematic`,
`placement-routing` or `artwork` stops at a recorded checkpoint. These return
`accepted:false`. A `CANCEL` file in the run directory stops before the next
stage; remove it and use `--resume` to continue. Mid-stage interruption retains
the attempt, and resumption starts a fresh attempt from the last completed
candidate. Native helpers retain their existing finite timeouts; placement and
routing share the declared job budget. Resumption within an interrupted router
trial is not yet connected to the build journal.

`build review` independently checks the last completed candidate, using the
scope generated by that build. It requires at least the schematic stage and
also works after a later stage fails. It ignores unfinished attempts and checks
the captured source, completed stage identities and candidate selection before
running any checks. A build writer excludes concurrent review; review leaves
the build unchanged and requires a new output directory outside it. It can
review a retained build from an older implementation: the original builder
identity is recorded alongside the ordinary review's current tool identities.

The diagnostic directory contains `source.json` with the selected build report,
stage, scope and runtime identities; `scope.json` with the actual candidate
inputs; `review/` with the ordinary native check evidence; and `report.json`
with each check's execution and outcome. Source selection is also captured as
`review/inputs/build-review/source.json`, so subsequent `agent-ee verify`
checks its custody. The `build-review/` candidate namespace is reserved for
this provenance. Authored checks, severities, baseline and limitations remain
unchanged. This command always reports `accepted:false`; exit 1 denotes an
incomplete review, even when every declared check passes. Inspect the individual
checks and unresolved requirements in `report.json` and `review/report.json`.
Successful evidence verification alone does not accept a manufacturing package.

With `--profile PROFILE`, `build review` also runs the profile's isolated
reviewers and fresh adjudicator through the ordinary full review against the
same selected candidate and generated scope. The profile is an explicit input;
reviewers use only the routes it declares, and a launch, authentication or
quota failure leaves that execution failed rather than switching route.
`qualification.json` then projects `engineering_review` from that review:
`pass` for `criteria_satisfied`, `failed` for `defects_or_unresolved`, bound to
the selected board hash, scope hash and stage. A failed or missing reviewer,
missing adjudication or any other incomplete outcome stays `not_assessed`.
The report still says `accepted:false` and `file_release` stays
`not_assessed`; the retained build is unchanged. Without `--profile` the
command is the checks-only review described above.

## Qualification and current claims

Each new run writes `qualification.json` (`agent-ee.qualification/1`) at the
run root and binds its hash in `build-report.json`. The record separates checks,
software file release, operational execution/resume, engineering review,
engineering judgments, supplier confirmation and physical validation. Read each
dimension with its candidate/scope binding and evidence. A checkpoint does not
make checks pass. A passing checks-only diagnostic remains `accepted:false` and
exits 1; its qualification assesses checks only.

The legacy `agent-ee.build-plan/1` continues to generate through every supported
stage. Its unchanged final package gate can establish its legacy file release;
the qualification record says `mode: legacy`, `claims_withheld: true` and reports
source-method coverage as unknown. Earlier reports are historical evidence, not
qualification of the current implementation.

Typed `agent-ee.build-plan/2` uses a [requirement-map/2](requirement-map.md) and
adds `requirements.obligations`, the relative path of an authored
`agent-ee.obligations/1` file. An optional top-level `judgments` names a normalized
relative directory, for example `"judgments": "judgments"`. A `/1` map cannot
be mixed with typed obligations, and a `/2` map cannot omit them. The existing
compiler still owns source spans, obligation kinds and method binding; the build
consumer does not infer evidence methods from requirement prose or ids.

Typed `accepted:true` means `qualification.dimensions.file_release.status` is
`pass`: the final package gate and required executable spans passed, required
judgments have independent concurrence, applicable sourced-rule evaluations are
available, and the current decision matches native stackup evidence. Unknown,
missing, skipped or stale required file evidence blocks that claim. This is a
software file claim. Supplier and physical dimensions stay pending, and every
outstanding delivery, judgment or physical obligation remains visible in
`coverage` and `summary.pending_required`.

Operational assessment supports only the explicitly compiled
`public_build_and_resume` criterion. It requires all seven verified stage trees
and an interrupted/failed attempt followed by the completed attempt of that
same stage under the same run identity. A clean first run reports operational
pending; a package or an unrelated resume cannot satisfy arbitrary operational
prose. Changed live inputs or invocation runtime refuse resume in a separate
receipt; they do not rewrite the retained build's claims. Corrupted retained
source or completed-stage evidence withdraws the current claim and records
operational failure while preserving previous root records and completed stage
bytes. Diagnostic checkpoints keep
exit 0 and `accepted:false`.

Qualification runs under the build's lock after stage receipts are sealed. It
hashes those files and publishes only a run-root record; `accepted-package.json`
contains no qualification reference. A complete run enters `status: assessing`
with `accepted:false` before this assessment. A crash or assessment failure can
resume with all seven stages already completed: only verification and assessment
repeat. The record is regenerated from receipts, including for an accepted run;
an edited old `qualification.json` is never adopted as evidence.
Fully generated files with missing evidence, such as a judgment awaiting its
witness, have `file_release: pending`, run `status: pending`, `accepted:false`
and exit 1. Demonstrated defects or stale/mismatched retained evidence are
`failed`; pending evidence does not assert a defect.
The latest failed package attempt can also supply an ordinary review whose own
evidence seal verifies. Its checks remain bound to that failed candidate; they
cannot adopt it or grant file release. This preserves actual failed-check
evidence when the package stage has no completed receipt.

Resume checks retained custody under its lock before comparing the proposed
invocation. A different live source, plan, runtime or frozen judgment input
creates a bounded `resume-refusals/<id>.json` (`agent-ee.resume-refusal/1`) and
returns nonzero. The receipt records the reason, attempted identity and input
hashes, retained identity, and hashes of the unchanged report and qualification.
These are refused invocations, not changes to the historical build outcome.
An ordinary review verifier can also refuse the current tools or rules after
retained stage custody passes; that refusal is recorded separately.

An older run without `build-plan.json` and without a qualification reference
is historical. Resume explicitly refuses unsupported migration, preserves its
report bytes and does not add a plan or current qualification. Its earlier
acceptance does not establish current typed method coverage. A qualified run
whose captured plan disappears instead fails retained custody.

On retained corruption, exact previous root report/qualification bytes and
hashes are saved under `superseded/<id>/`, with a `supersession.json` receipt.
The current report becomes `failed`, `accepted:false`; its qualification grants
no file claim and links the supersession. Reassessment of a previously accepted
run also saves the previous root records before replacing them. The archived
acceptance is historical evidence, not a valid current claim on corrupted files.
The maintainer [resume regression probe](../tests/qualification_resume_probe.py)
accepts `--plan`, `--run` and a new `--out` directory. Run it in the supported
runtime against an already qualified build. It verifies a real package gate,
changes only copies, and checks refusal bytes, migration and corruption; a
typed input also exercises its frozen judgment directory.

## Authored judgments and package records

Judgment paths in the typed map are relative to the declared judgments
directory. No stage before package reads or copies that directory. At package
entry the build freezes it beside the package candidate, writes
`judgment-inventory.json` and `applicability-inventory.json`, and binds the
inventory hash in the accepted-package record. Once frozen, a changed or added
record requires a new run, including after a failed package attempt. Resumption
refuses `judgment inputs changed after package` rather than re-evaluating new
testimony inside an old run.

Records use `agent-ee.engineering-judgment/1` and bind the requirement's exact
source span/hash, captured inputs, sources, applicability and author metadata.
Candidate-specific records also bind the final board hash and the authored
scaffold scope hash, which is available from diagnostic source selection.
Candidate-independent records require nonempty inputs and applicability.
Supported applicability facts are `board_thickness_mm`, `profile_sha256`,
`envelope_sha256`, `layer_count` and `max_component_height_mm`; another condition
refuses admission. Sources and input hashes must resolve against the frozen
candidate; a label or a valid JSON shape cannot supply an engineering result.
PDF sources require a captured UTF-8 text extract containing the cited quote.
Capture the original PDF and a provenance record that traces the extract to
its PDF hash, pages/locators and extraction tool/version. Bind those inputs in
the judgment; cite the extract's path and hash. The consumer resolves text
citations, not raw PDF contents; the author and independent verifier must check
the extraction provenance.

Witnesses under `judgments/verification/` use
`agent-ee.judgment-verification/1`, bind the judgment's file hash, identify a
verifier independent of its author, and record `concur` or `dissent` with defects.
The `checked` list contains exactly `source_citations_resolved`,
`applicability_recomputed` and `conclusion_consistent_with_bound_checks`.
Author and verifier identities are authored metadata, not authenticated
identities. Independence admission compares their names; the chief verifies
witness provenance out of band. These are the verifier's attestations; the build never authors a witness or
converts testimony into a full review. Admitted testimony is `recorded`, never
`pass`. Missing concurrence stays pending; dissent, stale bindings and unresolved
defects block the dependent file claim.

The rules register retains ERC/DRC ignored categories, native severities,
waivers, constraint classes, default advisories and sourced-limit evidence. It
does not regrade or promote defaults. The decision section identifies the
captured envelope/profile, nominal thickness, height limit and stackup evidence;
an older `manufacturing-decision.json` is preserved by hash in `supersedes`.

Package roundtrip and orientation are assessed from verified check rows.
Orientation also retains the package producer's assembly-profile assessment;
unassessed rows remain pending. An executable obligation bound to either record
blocks file release while its required evidence is pending. Software completion
does not perform or confirm a supplier preview or a physical test.

For a default manufacturing run, before placement/routing the build requires declared ERC, DRC, netlist,
geometry, parts membership, placement, board envelope, manufacturing profile,
assembly readiness and package checks. The profile and membership must name
the same envelope and parts used by generation. Unresolved requirement
limitations refuse this path. These are minimum coverage gates; the authored
electrical and mechanical requirements still determine the necessary checks.
An explicit `--through placement-routing` or `--through artwork` diagnostic can
proceed with incomplete coverage, recorded in the placement stage's
`manufacturing-coverage.json`. This permits analysis that needs the actual routed
copper. Declared placement constraints and native routing checks remain active;
the checkpoint is never accepted. Resuming toward the default package target
reapplies manufacturing coverage, even after a successful diagnostic route.

After routing, the artwork stage runs the existing bounded native silk repair
through an ordinary implementation receipt. It selects visible Reference/Value
fields and explicitly declared movable custom fields on silk layers. Only their
positions may change. Copper, component poses, footprints, marking content,
style, angle, visibility and graphics remain unchanged; the stage independently
replays that scope proof against the receipted board and tool identity. In
particular, pin-1 and polarity graphics are not translated by this default step.
Remaining native silk conflicts fail the stage with its report and source intact.
If there are no movable fields, it records a no-op; the final release check still
rejects remaining graphic conflicts. This does not waive final mechanical,
placement or manufacturing verification.

The final stage independently runs and verifies the ordinary checks-only review.
Every acceptance-mapped check must return `ok/pass`; missing, unknown or failed
checks do not pass. Exactly one passing `fab_package` must bind the final board
hash. The report then identifies its accepted native files and package artifacts.
Physical bench obligations are retained separately. Neither physical validation
nor supplier preview is recorded as performed.

It is tooling evidence, not qualification of a sourced device. The
